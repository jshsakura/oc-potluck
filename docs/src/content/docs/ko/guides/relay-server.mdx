중계 서버는 원격 플레이에만 필요합니다. 방 검색과 통신 중계를 맡고 Redis는 통계를 저장합니다. GitHub Pages는 이 문서용 정적 호스팅이며 **중계 서버를 실행하지 않습니다.**

Docker는 필수가 아닙니다. .NET으로 직접 빌드해 실행하려면 [소스로 중계 서버 실행](../relay-native/)을 참고하세요.

## 준비물

- Compose v2가 가능한 Docker 호스트와 지원 CPU(amd64·arm64). 임의의 32비트 ARM NAS에서는 이 예제를 사용할 수 없습니다.
- 중계 서버 1 GiB + Redis 256 MiB의 제한 외에 OS와 다른 앱을 위한 여유 메모리. 이 수치는 상한이며 실측 최소 사용량·보장 인원수가 아닙니다.
- 참가자에게 연결 가능한 TCP 30456. Redis는 내부에만 둡니다.

GUI 절차는 [시놀로지·NAS 안내](../synology/)를 참고하세요.

## 파일을 받고 시작

빈 배포 폴더(예: `potluck/`)에 [compose.nas.yml](/oc-potluck/downloads/compose.nas.yml)을 저장합니다. [저장소 원본](https://github.com/jshsakura/oc-potluck/blob/main/deploy/compose.nas.yml)도 사용할 수 있습니다. 내용을 확인한 뒤 그 폴더에서 실행하세요.

```sh
docker compose -f compose.nas.yml config --quiet
docker compose -f compose.nas.yml pull
docker compose -f compose.nas.yml up -d
docker compose -f compose.nas.yml ps
docker compose -f compose.nas.yml logs --tail=100 ldn-server redis
```

Redis가 healthy가 되고 `ldn-server`가 계속 실행되는지 확인합니다. 실행 중이라고 외부 접근까지 검증된 것은 아닙니다. PotLuck에 호스트 주소·포트를 입력해 연결 시험을 하고 두 기기로 방도 확인하세요.

## 배포 옵션

선택적으로 Compose 옆에 `.env`를 만듭니다.

```dotenv
LDN_SERVER_IMAGE=ghcr.io/jshsakura/oc-potluck-server:v0.2.3
LDN_BIND_IP=0.0.0.0
LDN_PORT=30456
```

| 변수 | 효과 | 변경할 때 |
| --- | --- | --- |
| `LDN_SERVER_IMAGE` | 고정 중계 이미지 태그. 모듈·서버 버전은 별개 | 검토한 서버 릴리스로 업데이트·롤백 |
| `LDN_BIND_IP` | Docker가 포트를 공개할 호스트 주소 | 특정 인터페이스로 제한. `127.0.0.1`이면 LAN에서 직접 접근 불가 |
| `LDN_PORT` | **호스트 쪽** TCP 포트 | 충돌 시 예를 들어 `30457`로 변경하고 기기도 동일하게 설정. 컨테이너 안은 계속 30456 |

수정 후 `up -d`로 재생성합니다. 이 변수는 Compose가 파일을 치환하는 값입니다. 컨테이너 내부 서버에는 environment 블록의 `LDN_PORT=30456`이 전달됩니다. 호스트 포트와 내부 포트를 혼동하지 마세요.

예제 내부 설정은 다음과 같습니다.

| 항목 | 용도 |
| --- | --- |
| `LDN_HOST=0.0.0.0`, `LDN_PORT=30456` | 컨테이너 안의 중계 리스너 |
| `LDN_REDIS_HOST=redis`, `LDN_REDIS_PORT=6379` | 컨테이너 내부 통계 연결 |
| `IP_BAN_FILE_PATH=/data/potluck/bannedips.txt` | 이름 있는 볼륨의 차단 목록 경로 |
| `user: 10001:10001` | 비관리자 실행 계정. 바인드 폴더 권한과 관련 |
| `read_only`, 권한 제거, `no-new-privileges` | 컨테이너 권한 제한. 쓰기 경로만 명시적으로 허용 |
| `mem_limit`, `memswap_limit`, `pids_limit` | 자원 상한. 조절 전에 OOM·재시작 로그 확인 |
| `logging` | 서비스당 10 MB 로그 3개 순환 |

Redis는 호스트 포트를 공개하지 않고 중계 서버와 내부 네트워크를 공유합니다. `protected-mode no`는 이 격리 안에서만 사용합니다. **6379를 공개하거나 신뢰하지 않는 컨테이너를 연결하지 마세요.** 연결 문제 해결을 위해 host 네트워크·privileged 모드를 추가하지 마세요.

## 기기 연결

같은 LAN은 호스트의 내부 IPv4를 씁니다. 외부 참가자는 공개한 **TCP** 포트를 호스트의 예약된 내부 IP로 전달하고 호스트 방화벽에서도 허용한 뒤 공인 IP·DDNS로 접속합니다. 로컬 모드는 인터넷 포트 전달이 필요 없습니다. CGNAT·프록시는 [NAS 네트워크](../synology/)를 확인하세요.

현재 기기 통신은 일반 TCP입니다. 채널은 검색 구분이며 암호화·강한 인증이 아닙니다. 의도한 사용자에게 주소를 공유하고 가능하면 방화벽 접근 대상을 제한하세요. 일반 HTTP·TLS 프록시를 앞에 둔다고 이 클라이언트에 TLS가 지원되지는 않습니다.

## 데이터·백업·권한

기본 이름 있는 볼륨 `ldn-data`에 차단 목록을 보관하고 재생성 시 유지합니다. 실제 이름에는 Compose 프로젝트 접두사가 붙습니다. 업데이트 때 폴더·프로젝트 이름을 유지하세요. 바뀌면 새 빈 볼륨이 만들어질 수 있습니다. 중계 서버를 멈추고 호스트의 볼륨 백업 도구로 Compose·`.env`·데이터 볼륨을 백업하세요.

Redis는 `--save ''`, `--appendonly no`로 통계가 영속적이지 않습니다. 서버 재시작 때 방도 유지되지 않으므로 점검을 미리 알리세요.

이름 있는 볼륨은 NAS 바인드 폴더의 ACL 문제를 줄입니다. `./data:/data/potluck`으로 바꾼다면 폴더를 만들고 NAS 권한 도구로 **UID/GID 10001:10001**에 쓰기를 허용하세요. 모두 쓰기 권한이나 root 실행으로 우회하지 마세요.

## 업데이트·롤백

1. 플레이를 마치고 설정·볼륨을 백업한 뒤 릴리스 노트를 읽습니다.
2. `.env` 또는 image의 태그를 검토한 버전으로 바꿉니다. 이 예제는 `latest`를 자동 추적하지 않습니다.
3. 같은 파일·프로젝트로 `pull`, `up -d`를 실행하고 상태·로그·기기 연결을 확인합니다.
4. 롤백은 데이터 호환성 안내를 확인한 뒤 이전 태그로 바꾸고 같은 명령을 실행합니다.

```sh
docker compose -f compose.nas.yml stop
docker compose -f compose.nas.yml pull
docker compose -f compose.nas.yml up -d
```

`stop`은 컨테이너·볼륨을 보관합니다. `down`은 기본적으로 이름 있는 볼륨을 남기고 컨테이너·네트워크를 지웁니다. **`down -v`는 데이터 볼륨도 삭제합니다.** 지울 의도가 아니라면 NAS의 Clean·Delete에서 볼륨 삭제를 선택하지 마세요.

재시작 반복은 처음 관련 오류부터 확인하고 Redis 상태·CPU 아키텍처·폴더 권한을 점검하세요. [문제 해결](../troubleshooting/)에 보고 자료가 정리되어 있습니다.
