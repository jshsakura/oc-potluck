## NAS부터 확인하세요

Docker Compose와 중계 이미지의 amd64·arm64를 지원하는 NAS를 사용합니다. 시놀로지는 **프로젝트 기능이 있는 Container Manager**(지원 모델의 DSM 7.2 계열 패키지 이상)가 필요합니다. 지원하지 않는 모델도 있으므로 모델별 패키지 제공 여부를 확인하세요. Web Station 설치로 컨테이너 기능이 생기지는 않습니다. 예제의 컨테이너 메모리 상한은 합계 1.25 GiB이며 DSM·다른 앱을 위한 여유도 필요합니다.

프로젝트 마법사는 Compose YAML을 가져옵니다. [시놀로지 공식 프로젝트 도움말](https://kb.synology.com/en-global/DSM/help/ContainerManager/docker_project?version=7)을 참고하세요. DSM·패키지 버전에 따라 이름이 조금 다를 수 있습니다.

## Container Manager에서 만들기

1. 패키지 센터에서 **Container Manager**를 설치·실행합니다. File Station에서 `/volume1/docker/potluck` 같은 작업 폴더를 만듭니다.
2. 컴퓨터에 완전한 [Compose 예제](/oc-potluck/downloads/compose.nas.yml)를 저장합니다. **중계 서버와 Redis 모두**, 자원 제한·상태 검사·내부 네트워크·로그 순환이 들어 있습니다.
3. **프로젝트 → 생성**을 선택합니다. 프로젝트 이름은 `potluck`처럼 고정하고 위 작업 폴더를 지정합니다.
4. YAML을 업로드하거나 Compose 파일 생성 옵션으로 전체 내용을 붙여 넣습니다. Container Manager가 `compose.yaml`·`docker-compose.yaml`로 저장할 수 있으니 이후 SSH를 쓸 때는 실제 파일명을 확인하세요.
5. 이미지 태그와 공개 TCP 포트를 확인합니다. 처음에는 기본 이름 있는 볼륨을 유지하세요. HTTP 앱이 아니므로 **Web Station 웹 포털은 켜지 않습니다.**
6. 프로젝트를 시작합니다. 서비스·로그에서 Redis가 healthy이고 중계 서버가 실행을 유지하는지 확인합니다. 실패하면 반복 실행 전에 첫 오류를 읽으세요.

이미지 버전·호스트 포트 변경은 프로젝트 편집기에서 image·ports를 수정하거나 해당 버전에서 지원하는 `.env`를 사용합니다. [배포 옵션](../relay-server/)을 확인하세요. 변경 후에는 볼륨을 보관하며 프로젝트를 다시 생성·빌드합니다.

## 명령줄 대안: Compose를 지원하는 NAS

예제를 고정된 배포 폴더에 `compose.nas.yml`로 저장하고 그 폴더에서 실행합니다.

```sh
docker compose -f compose.nas.yml config --quiet
docker compose -f compose.nas.yml pull
docker compose -f compose.nas.yml up -d
docker compose -f compose.nas.yml ps
docker compose -f compose.nas.yml logs --tail=100 ldn-server redis
```

계정에 Docker 관리 권한이 필요합니다. Compose 플러그인이 없다면 임의의 컨테이너 명령으로 실행하지 말고 제조사가 지원하는 설치·프로젝트 UI를 사용하세요. 다른 NAS는 화면 이름이 다르지만 서비스·볼륨·네트워크 설정은 유지합니다.

## 먼저 같은 LAN에서 확인

라우터에서 NAS 주소를 고정 예약합니다. 예를 들어 `192.168.1.20`이라면 같은 LAN의 기기에서 서버 **`192.168.1.20`**, 포트 **`30456`**, **원격** 모드로 설정합니다. DSM·호스트 방화벽에서 참가 네트워크의 TCP 30456을 허용하세요. 연결 시험 후 P2P를 끄고 같은 서버·채널의 두 기기로 방을 확인합니다.

같은 LAN이어도 중계 서버를 시험할 때는 원격을 고르세요. 로컬은 서버를 거치지 않습니다. Docker 브리지 IP, `redis`, `http://192.168.1.20`, 문서 URL을 넣지 마세요.

## 외부 참가자 연결

1. 인터넷 회선이 외부에서 들어오는 연결을 받을 수 있는지 확인합니다. CGNAT·이중 NAT라면 ISP·라우터 설정 변경 또는 외부 접근이 가능한 별도 서버가 필요할 수 있습니다.
2. 라우터의 **TCP 30456**을 NAS의 예약된 내부 IP로 전달합니다. 호스트 포트를 바꿨다면 바뀐 포트로 모두 맞춥니다.
3. DSM 방화벽에서도 그 포트를 허용하고 가능하면 접근 대상을 제한합니다. Redis 6379·DSM 관리 포트를 PotLuck 때문에 공개하지 마세요.
4. 외부 기기에는 공인 IP·DDNS 호스트명을 경로·스킴 없이 입력합니다. 실제 다른 네트워크에서 시험하세요. NAT 루프백이 없는 라우터의 내부 기기는 LAN IP가 필요할 수 있습니다.

QuickConnect·Web Station은 일반 TCP 중계 터널이 아닙니다. HTTP 역방향 프록시나 웹 프록시가 켜진 DNS도 게임 프로토콜을 그대로 전달하지 않습니다. DDNS는 주소를 연결할 뿐 CGNAT·방화벽을 해제하지 않습니다. 클라이언트에서 켤 수 있는 TLS 스위치도 없습니다. 서버 접근 범위를 의도에 맞게 관리하세요.

## 저장소·권한 오류

예제는 **Docker가 관리하는 이름 있는 볼륨**을 씁니다. 프로젝트 폴더를 만들었다고 별도의 데이터 공유 폴더까지 쓰기 가능하게 만들 필요는 없습니다. 같은 볼륨을 쓰려면 프로젝트 이름을 유지하세요.

바인드 마운트를 선택하면 데이터 폴더를 만들고 NAS ACL·소유권 도구로 컨테이너의 숫자 UID/GID **10001:10001**에 쓰기를 허용합니다. DSM 로그인 계정이 쓸 수 있는 폴더여도 이 UID가 자동으로 쓸 수 있지는 않습니다. 서버 로그의 권한 오류를 확인하세요. `chmod 777`, privileged, root 실행으로 해결하지 마세요.

## 업데이트·백업·삭제

정지 전 참가자에게 알립니다. 중계 서버를 멈추고 프로젝트 YAML·사용 중인 `.env`·이름 있는 볼륨을 백업하세요. Redis 통계는 임시 데이터입니다. 검토한 이미지 태그로 바꾸고 같은 프로젝트·볼륨을 유지하며 다운로드·재생성한 뒤 상태와 기기 연결을 확인합니다. 서버 이미지 태그는 기기 모듈 버전과 별개입니다.

프로젝트 UI에서 컨테이너를 다시 만들거나 삭제할 때 볼륨을 보관하세요. Clean·Delete에 관련 데이터 삭제 옵션이 있으면 먼저 확인합니다. CLI의 `down -v`도 이름 있는 볼륨을 삭제합니다. 명령과 롤백은 [서버 운영](../relay-server/)을 따르세요.

## 계속 실패한다면

- **맞는 이미지 manifest가 없음:** NAS CPU를 확인하세요. 이 예제는 32비트 ARM을 지원하지 않습니다.
- **포트 사용 중:** 호스트 30457 → 컨테이너 30456처럼 바꾸고 기기·방화벽·라우터도 맞춥니다.
- **Redis unhealthy:** 로그·여유 메모리부터 확인합니다. 확인하려고 포트를 공개하지 마세요.
- **서버 정상, 외부만 실패:** LAN·외부 결과를 비교하고 포트 전달·DSM 방화벽·이중 NAT·CGNAT·실제 공인 주소를 봅니다.
- **권한 거부:** DSM 웹 로그인보다 볼륨 종류와 바인드 폴더 UID·ACL을 확인합니다.

이 안내는 배포 구성을 설명합니다. NAS 모델별 실기 동작은 해당 장비에서 확인해야 합니다. 게임 세션 문제는 [문제 해결](../troubleshooting/)을 보세요.
